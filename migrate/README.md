# Миграции: как есть и чего не хватает

Каталог пустой намеренно: здесь будет накатчик схемы Postgres, которого сегодня нет ни здесь,
ни в контроллере. Документ описывает дыру и требования к тому, что её закроет.

## Как сейчас

**ClickHouse — хорошо.** Схему накатывает логгер при старте: `logger/schema/*.sql` по порядку,
отметки в `waf.schema_migrations`, `waf.schema_lock` против гонки двух реплик. Базу создаёт сам
(`CREATE DATABASE IF NOT EXISTS waf`). Обновление установки = обновление образа логгера.

**Postgres — никак.** 103 файла `controller/schema/*.sql` применяются только через
`docker-entrypoint-initdb.d`, то есть **однократно и только на пустом томе**. Живая база
обновляется руками: оператор сам решает, какие файлы новые, и сам их скармливает. Отсюда и
знакомый симптом «база стенда отстаёт от `controller/schema`»: сверить их нечем, отметок о
применённом нет.

Для стенда это терпимо — том сносится. Для установки, которую кто-то обновит на версию выше,
это отсутствующий путь обновления.

## Что должно уметь

1. **Отмечать применённое.** Таблица версий в самой базе, как `waf.schema_migrations` у логгера.
2. **Не пускать двоих.** Блокировка на время прохода: две реплики контроллера стартуют
   одновременно, и обе видят непроведённую миграцию (`schema_lock` у логгера — рабочая модель,
   но у Postgres для этого есть honest `pg_advisory_lock`).
3. **Падать громко.** Ошибка миграции — отказ старта, а не запуск на схеме, которой код не
   соответствует.
4. **Идти вперёд и только вперёд.** Откат — отдельный файл, а не автоматика: обратная миграция,
   применённая на живых данных, теряет их молча.
5. **Проверяться до применения.** Отдельная команда «что бы накатилось» для установки, которую
   обновляют по регламенту.

## Где ему жить

Два варианта, оба защитимы, и выбирать надо один раз.

**В контроллере** — по правилу «кто пишет в таблицу, тот и объявляет таблицу». Тогда DDL и код
выпускаются вместе и разъехаться не могут, а `core` только поднимает базу. Минус: обновление
установки идёт через запуск компонента, а не отдельной командой фундамента.

**В core** — тогда установка обновляется одной командой независимо от компонентов, а порядок
(сначала схема, потом процессы) виден явно. Минус: версия схемы и версия кода выпускаются
порознь, и «контроллер 1.4 на схеме 1.2» становится возможен.

Предложение из `docs/repos.md` платформы: **накатчик у владельца данных, запуск — из
`core`**. `core` знает порядок и дёргает образ компонента (`docker compose run --rm controller
migrate`), а DDL и его код едут вместе.

## Пока его нет

Накатить схему на пустой том:

```sh
docker compose up -d postgres        # initdb прочитает WAF_PG_INITDB
```

Догнать живую базу — руками, по одному файлу, сверяясь с тем, что уже применено:

```sh
docker compose exec -T postgres psql -U waf -d waf -f /docker-entrypoint-initdb.d/0NN_имя.sql
```
