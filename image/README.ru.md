# Образ виртуальной машины

[English](README.md) · Русский

Готовая виртуальная машина: Debian 13, Docker, все образы Placitum, а ещё nginx с модулем и haproxy
с их агентами службами самой машины. В самом образе ещё ничего не установлено. Первый запуск спрашивает настройки на консоли и создаёт свои ключи и пароли, поэтому
у машин из одного образа общих секретов нет.

## Сборка

На Linux-машине с Docker и KVM:

```sh
sh image/build.sh
```

Скрипт собирает образы по `sources.env`, запускает облачный образ Debian 13 в QEMU, ставит туда
Docker, загружает образы, ставит на машину nginx и haproxy с их агентами (`image/host.sh`) и
вычищает машину. Результат — `image/work/placitum-<ревизия>.qcow2`,
около 2 ГБ. Ветки из `sources.env` превращаются в коммиты, образ перечисляет их в
`/opt/placitum/image/MANIFEST`.

Сборка грузит все ядра машины. Если маленькая машина перегревается, собирайте образы компонентов
по одному и дайте сборочной машине два ядра: `BUILD_ONE_BY_ONE=1 VM_CPUS=2 sh image/build.sh`.
`BUILD_PAUSE` выполняет команду перед каждым образом: `BUILD_PAUSE="sh image/cool.sh"` ждёт, пока
процессор остынет ниже 70 градусов (`COOL_BELOW`).

Сборочной машине нужны Docker, `qemu-system-x86_64` с доступом к `/dev/kvm` (группа `kvm`),
`qemu-img`, `cloud-localds` из cloud-image-utils, `ssh`, `curl` и `python3`, а ещё интернет: пакеты
Debian и Docker ставятся из их репозиториев.

## Форматы

Сборка делает qcow2 для KVM. `image/export.sh` превращает его в форматы других гипервизоров;
машина внутри та же, первый запуск идёт так же.

```sh
sh image/export.sh image/work/placitum-<ревизия>.qcow2        # оба формата
sh image/export.sh image/work/placitum-<ревизия>.qcow2 vhdx   # только Hyper-V
```

| Файл | Гипервизор | Как запустить |
| --- | --- | --- |
| `placitum-<ревизия>.qcow2` | KVM, QEMU, Proxmox | диск и сетевой адаптер virtio, BIOS или UEFI; `image/check.sh kvm` загружает его под QEMU |
| `placitum-<ревизия>.vhdx` | Hyper-V | машина второго поколения с Secure Boot по шаблону Microsoft UEFI Certificate Authority или первого поколения; диск на контроллере SCSI, 2 процессора, 4 ГБ, сетевой адаптер на внешнем коммутаторе |
| `placitum-<ревизия>.ova` | VirtualBox, VMware Workstation, ESXi | импортировать OVA: в нём 2 процессора, 4 ГБ, контроллер LSI Logic SCSI и адаптер Intel E1000; адаптер — в ту сеть, из которой открывают панель (bridged) |

Образ собирается на облачном образе Debian `generic`, у ядра которого есть драйверы устройств,
которые эти гипервизоры эмулируют. `--base genericcloud` берёт вместо него меньшее облачное ядро,
которое знает только KVM, Xen и паравиртуальные устройства Hyper-V и VMware: VirtualBox с ним не
работает, VMware — только с паравиртуальным SCSI и vmxnet3.

Вне KVM у cloud-init нет seed, поэтому первый запуск задаёт вопросы на консоли машины; файл ответов
работает там, где гипервизор отдаёт cloud-init seed NoCloud.

## Проверка сборки

`image/check.sh` загружает диск под QEMU с устройствами нужного гипервизора, ждёт приглашение входа
на последовательной консоли и выключает машину; сам диск не меняется. Видно, нашло ли ядро диск и
сетевой адаптер, поднялся ли ssh и начался ли первый запуск.

```sh
sh image/check.sh kvm    image/work/placitum-<ревизия>.qcow2   # virtio, BIOS
sh image/check.sh hyperv image/work/placitum-<ревизия>.vhdx    # UEFI, диск на SCSI
tar -xf image/work/placitum-<ревизия>.ova                      # диск из OVA
sh image/check.sh ide    placitum-<ревизия>-disk1.vmdk         # IDE и E1000, как при импорте
sh image/check.sh sata   placitum-<ревизия>-disk1.vmdk         # после переноса на контроллер SATA
```

Машине проверки нужны `qemu-system-x86_64` с KVM, `qemu-img`, `python3`, а для `hyperv` — прошивка
OVMF из пакета `ovmf`. Это проверка загрузки, а не установки: весь первый запуск с установкой
проверяется на KVM с файлом ответов, см. [Первый запуск](#первый-запуск).

Выпуск — три команды подряд: `build.sh`, `export.sh`, `check.sh` для каждого файла, потом сами файлы
с их `sha256sum`.

## Файлы

| Файл | Что делает |
| --- | --- |
| `build.sh` | собирает образы компонентов, готовит машину Debian в QEMU и пишет qcow2 |
| `provision.sh` | работает внутри сборочной машины: Docker, образы, файлы Placitum, службы машины, служба первого запуска, зачистка |
| `host.sh` | nginx с модулем и агентом узла, haproxy с агентом — службами машины, из образов; `install.sh` тоже зовёт его, где может |
| `export.sh` | VHDX для Hyper-V и OVA для VirtualBox и VMware из qcow2 |
| `check.sh` | загружает диск под QEMU с устройствами гипервизора и случайным адресом адаптера |
| `cool.sh` | ждёт, пока остынет процессор, для `BUILD_PAUSE` |
| `firstboot.sh`, `placitum-firstboot.service` | первый запуск на консоли: пароль пользователя `placitum` и установка |
| `placitum` | `sudo placitum <команда>` на машине, команды `install.sh` без сборок |
| `balancer/`, `node/` | юниты и заглушки конфигураций haproxy и nginx на машине |
| `network/` | конфигурация сети машины для netplan и файл, которым cloud-init отдаёт сеть ей |

## Сеть

Машина получает адрес по DHCP на том сетевом адаптере, какой ей дали: `/etc/netplan/99-placitum.yaml`
подбирает адаптеры по имени (`en*` и `eth*`), а не по аппаратному адресу, поэтому один и тот же
образ работает на любом гипервизоре. Сеть здесь не настраивает cloud-init: его конфигурация
привязана к тому адаптеру, который он увидел, и образ увёз бы её на машины с другими адаптерами.
Постоянный адрес задаётся в том же файле, дальше `netplan apply`.

Приглашение на консоли показывает адрес машины ещё до входа. Пустой адрес в этой строке означает,
что машина не получила аренду, и панель не видна ниоткуда, кроме неё самой.

## Первый запуск

Первый запуск проводит установку на консоли (tty1):

1. Пароль пользователя `placitum`. Под ним входят на консоли и по SSH, у него есть sudo.
2. Настройки установки: имя узла, адреса и порты трафика, адрес и порт панели, сеть для
   контейнеров. Ещё один вопрос открывает узлы, процессы nginx, копии инспекторов и память Redis. Enter берёт значение в скобках. Адрес
   панели по умолчанию `0.0.0.0`, все адреса машины.
3. Пароль пользователя панели `admin`. Enter генерирует пароль и показывает его один раз.

Образы уже на диске, поэтому ничего не скачивается, и установка идёт около минуты. В конце консоль
показывает адрес панели; приглашение ко входу тоже его показывает.

Без консоли, например в облаке, ответы кладут в `/etc/placitum/answers.env` до первого запуска.
Через cloud-init:

```yaml
#cloud-config
write_files:
  - path: /etc/placitum/answers.env
    permissions: "0600"
    content: |
      PLC_NODE_ID=edge-01
      PLC_PANEL_PASSWORD=длинный-пароль
```

Переменные те же, что в `.env.example`. Недостающие берут значения по умолчанию. После чтения файл
удаляется. Ключи SSH и пользователи в этом случае приходят из cloud-init как обычно.

## На машине

| Команда | Что делает |
| --- | --- |
| `sudo placitum reconfigure` | заново спрашивает настройки и применяет их |
| `sudo placitum status` | показывает, что запущено, и адреса |
| `sudo placitum panel-password` | меняет пароль `admin` и снимает блокировку входа |
| `sudo placitum check` | проверяет настройки, ничего не меняя |
| `sudo placitum down` | останавливает всё; данные остаются |

`placitum` запускает `/opt/placitum/install.sh` и никогда не собирает образы. Настройки лежат в
`/opt/placitum/.env`.

При одном узле nginx с модулем работает прямо на машине, службами `nginx` и `placitum-node-agent`,
в контейнерах — только остальное; при нескольких узлах узлы — контейнеры, а на машине работает
haproxy с агентом, службы `placitum-haproxy` и `placitum-haproxy-agent`. `placitum reconfigure`
включает и выключает их, конфигурацию агенты берут у контроллера. Подробнее: [Где работает
узел](../INSTALL.ru.md#где-работает-узел).

## Размер машины

Самая маленькая машина — 2 ядра, 4 ГБ памяти и диск 20 ГБ. Замеры на KVM нагрузочными кейсами
стенда. Тестовое приложение работало на той же машине и занимало до пятой части ядра.

| Проверки на маршруте | Запросов в секунду без ошибок | p99 |
| --- | --- | --- |
| Правила ModSecurity, CRS на первом уровне параноидальности | 750; 500 в течение пяти минут | 120–250 мс |
| Десять поисков по спискам адресов | 560 | 110 мс |
| Калитка по JWT, счётчик запросов и тело ответа | 340 | 60 мс |

Первым кончается процессор. Свободной памяти под нагрузкой остаётся от 1,3 ГБ. Долгий предел —
диск: каждый запрос оставляет в ClickHouse около 270 байт, аудит хранится 90 дней, журнал 14. При
постоянных 100 запросах в секунду это около 2,3 ГБ в сутки.

## Чего пока нет

- Hyper-V, VirtualBox и VMware сами не проверялись: VHDX и диск из OVA загружались под QEMU с UEFI и с
  контроллером LSI Logic и адаптером E1000 — устройствами, которые эти гипервизоры показывают.
- Обновления: новая версия — новая машина.
- Внешнего S3 вместо локального MinIO в настройках.
- Классификатора `vlai`: в образе нет ни его образа, ни модели, и установка его не предлагает.
- HTTPS для панели: по обычному HTTP пароль идёт открытым текстом.
