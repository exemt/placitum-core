# Миграции: кто накатывает и как

Каталог пустой намеренно: накатчик схемы Postgres живёт в контроллере (`src/migrate.ts`), а
здесь — почему так, что он обязан делать и как это выглядит из установки.

## Как сейчас

**ClickHouse — хорошо.** Схему накатывает логгер при старте: `logger/schema/*.sql` по порядку,
отметки в `waf.schema_migrations`, `waf.schema_lock` против гонки двух реплик. Базу создаёт сам
(`CREATE DATABASE IF NOT EXISTS waf`). Обновление установки = обновление образа логгера.

**Postgres — так же, с 12.09.2026.** У контроллера есть поставочная база — `01-baseline.sql`
(структура), `02-shipped.sql` (данные поставки, вместе с заполненным журналом `waf_schema_log`),
`03-geo.sh` — и архив миграций в `migrations/`. Всё это едет в его образе (`/app/schema`), и при
старте контроллер накатывает сам: пустая база получает поставку 1.0 и миграции новее неё, живая —
только то, чего нет в журнале. Отдельный запуск `node src/migrate.ts --check` показывает план,
ничего не применяя.

## Где ему жить: в контроллере

Решение 12.09.2026. Накатывает **контроллер, при старте** — так же, как логгер накатывает
ClickHouse. Причины, по которым выбран он, а не `core`:

- **Одна версия на схему и на код.** DDL едет тем же образом, что и код, который в эти таблицы
  пишет. «Контроллер 1.4 на схеме 1.2» становится невозможным, а это ровно тот перекос, который
  дороже всего чинить на чужой установке.
- **Обновление = обновление образа.** Ни отдельного шага в установщике, ни Job в Kubernetes,
  ни порядка, который надо помнить.
- **Модель уже проверена** на логгере: `schema_migrations` плюс блокировка, две реплики не дерутся.
- **Писатель один.** В эту схему пишет только контроллер; у `core` нет ни причины знать её
  таблицы, ни способа проверить, что накатанное соответствует коду.

`core` при этом отвечает за порядок — поднять Postgres и дождаться его готовности, — и больше
ни за что. Как только накатчик появится, `WAF_PG_INITDB` из установки уходит: схему на пустой
базе поднимет тот же контроллер, и файлы схемы не понадобятся ни на диске установки, ни в
`initdb`.

### Что он обязан делать

1. **Отмечать применённое** в `waf_schema_log` — таблица уже есть и приходит с поставкой
   отмеченной по весь архив.
2. **Не пускать двоих.** `pg_advisory_lock` на время прохода: две реплики стартуют одновременно,
   и обе видят непроведённую миграцию.
3. **Падать громко.** Ошибка миграции — отказ старта, а не работа на схеме, которой код не
   соответствует.
4. **Идти вперёд и только вперёд.** Откат — отдельный файл, а не автоматика: обратная миграция
   на живых данных теряет их молча.
5. **Уметь показать, не применяя.** `migrate --check` печатает, что бы накатилось: установка,
   которую обновляют по регламенту, обязана уметь показать это DBA до окна работ.
6. **Не трогать данные поставки.** `02-shipped.sql` — наполнение пустой базы, а не миграция:
   применённый повторно, он затрёт то, что оператор поменял.

### Правило совместимости

Во время раскатки на одной схеме какое-то время работают **две версии кода** — старая реплика
и новая. Значит миграция обязана быть совместимой с предыдущим релизом: колонку добавили —
выкатили код — и только следующим релизом убрали старую. Ломающее изменение в один шаг означает
простой панели, а не «немного ошибок в логе».

### Чего накатчик не делает

Каталог гео (`03-geo.sh` и `seed/*.sql`) — операторский шаг, а не миграция: выгрузка MaxMind
лицензируется отдельно, весит сотню мегабайт и в образ не едет.

## Как это выглядит из установки

Шаг `migrate` в `install.sh` запускает накатчик из образа контроллера до старта процессов —
сначала план, потом применение:

```sh
docker compose -f compose/waf.yml run --rm --no-deps controller node src/migrate.ts --check
docker compose -f compose/waf.yml run --rm --no-deps controller node src/migrate.ts
```

Тот же накатчик отработает и при старте контроллера, поэтому шаг нужен не ради схемы, а ради
порядка и отчёта: видно, что именно применилось, до того как поднялся контур.

Три состояния базы и что накатчик с ними делает:

| База | Что делает |
| --- | --- |
| Пустая | `01-baseline.sql`, `02-shipped.sql`, затем миграции новее поставки |
| С журналом | только файлы `migrations/`, которых в журнале нет |
| Схема есть, журнала нет | отказ: база старше поставки 1.0. `CONTROLLER_SCHEMA_BASE=NNN` один раз называет последнюю применённую миграцию, дальше журнал ведётся сам |

`WAF_PG_INITDB` установке больше не нужен: схему на пустой базе поднимает контроллер. Стенд
платформы им пока пользуется — там в initdb едут ещё гео-сид и стендовое дерево.

Каталог гео (`03-geo.sh`, `seed/*.sql`) накатчик не трогает: это операторский шаг.
