# Миграции: как есть и чего не хватает

Каталог пустой намеренно: накатчика схемы Postgres нет ни здесь, ни в контроллере, и пока
его пишут, документ держит требования к нему и обходные пути.

## Как сейчас

**ClickHouse — хорошо.** Схему накатывает логгер при старте: `logger/schema/*.sql` по порядку,
отметки в `waf.schema_migrations`, `waf.schema_lock` против гонки двух реплик. Базу создаёт сам
(`CREATE DATABASE IF NOT EXISTS waf`). Обновление установки = обновление образа логгера.

**Postgres — половина пути пройдена.** С 12.09.2026 у контроллера есть поставочная база:
`controller/schema/01-baseline.sql` (структура), `02-shipped.sql` (данные поставки) и
`03-geo.sh`, а архив миграций убран в `migrations/`. Журнал применённого — таблица
`waf_schema_log`, и она приходит вместе с поставкой отмеченной по весь архив. Пустой том
поднимается правильной базой, и это большой шаг.

Чего по-прежнему нет — **накатчика для живой установки**: файл `migrations/1NN_*.sql`, выпущенный
после поставки, никто не применит. И второе, специфичное для установки из `core`: **образ
контроллера каталог `schema/` не везёт вовсе** (`controller/Dockerfile` копирует только `src` и
собранную панель), поэтому у установки, собранной из репозиториев, этих файлов нет ни на диске,
ни в образе.

Отсюда два обязательных шага, и оба — в контроллере, а не здесь: класть `schema/` в образ и
дать команду, которая её накатывает.

## Что должно уметь

1. **Отмечать применённое.** Таблица версий в самой базе, как `waf.schema_migrations` у логгера.
2. **Не пускать двоих.** Блокировка на время прохода: две реплики контроллера стартуют
   одновременно, и обе видят непроведённую миграцию (`schema_lock` у логгера — рабочая модель,
   но у Postgres для этого есть honest `pg_advisory_lock`).
3. **Падать громко.** Ошибка миграции — отказ старта, а не запуск на схеме, которой код не
   соответствует.
4. **Идти вперёд и только вперёд.** Откат — отдельный файл, а не автоматика: обратная миграция,
   применённая на живых данных, теряет их молча.
5. **Проверяться до применения.** Отдельная команда «что бы накатилось» для установки, которую
   обновляют по регламенту.

## Где ему жить

Два варианта, оба защитимы, и выбирать надо один раз.

**В контроллере** — по правилу «кто пишет в таблицу, тот и объявляет таблицу». Тогда DDL и код
выпускаются вместе и разъехаться не могут, а `core` только поднимает базу. Минус: обновление
установки идёт через запуск компонента, а не отдельной командой фундамента.

**В core** — тогда установка обновляется одной командой независимо от компонентов, а порядок
(сначала схема, потом процессы) виден явно. Минус: версия схемы и версия кода выпускаются
порознь, и «контроллер 1.4 на схеме 1.2» становится возможен.

Предложение из `docs/repos.md` платформы: **накатчик у владельца данных, запуск — из
`core`**. `core` знает порядок и дёргает образ компонента (`docker compose run --rm controller
migrate`), а DDL и его код едут вместе.

## Пока его нет

На **пустом** томе всё работает само, если установка дала postgres каталог со схемой:

```sh
docker compose up -d postgres        # initdb прочитает WAF_PG_INITDB
```

Postgres читает оттуда только верхний уровень: `01-baseline.sql`, `02-shipped.sql`, `03-geo.sh`.
Подкаталоги (`migrations/`, `stand/`, `seed/`) он пропускает — на этом раскладка и держится.

В установке из репозиториев этого каталога взять негде, пока образ контроллера его не везёт.
Обходной путь на сегодня — выкачать схему рядом с `core` и указать на неё:

```sh
git clone --depth 1 https://github.com/exemt/placitum-controller.git /tmp/ctl
WAF_PG_INITDB=/tmp/ctl/schema docker compose -f compose/infra.yml up -d postgres
```

Живую базу догоняют руками, сверяясь с `waf_schema_log`:

```sh
docker compose exec -T postgres psql -U waf -d waf   -c "select version from waf_schema_log order by version desc limit 5"
docker compose exec -T postgres psql -U waf -d waf -f /path/to/migrations/1NN_имя.sql
```
