# Установка

[English](INSTALL.md) · Русский

Что нужно машине, как настраивается установка и как проверить, что всё работает. Быстрый старт и
состав репозитория — в [README.ru.md](README.ru.md).

## Что нужно

| Что | Сколько |
| --- | --- |
| Docker | 24 или новее, с BuildKit |
| Docker Compose | 2.20 или новее: установка держится на `include` |
| Ядра и память | не меньше 2 ядер и 4 ГБ, см. [замеры](image/README.ru.md#размер-машины); 8 ядер и 16 ГБ для большого трафика; с `vlai` ещё 4 ГБ |
| Диск | 20 ГБ на образы, кеши сборки и данные; архив тел растёт со временем |
| Сеть | на время сборки: GitHub, Docker Hub, quay.io, proxy.golang.org, npm, PyPI |

Образы собираются из исходников на этой же машине, готовых установка не качает. Первая сборка
занимает несколько минут: модуль nginx компилируется против исходников nginx, собирается панель.
Это не зависание.

Установка без интернета — отдельная история: сборке нужны зеркала реестров и модулей, они
подставляются через `GOPROXY` и переменные источников.

## Установка

```sh
git clone https://github.com/exemt/placitum-core.git
cd placitum-core
./install.sh check
./install.sh install
```

`install` идёт по шагам и останавливается на первой ошибке:

1. **Проверки**: Docker, Compose, `openssl`, место на диске, файл источников.
2. **Настройки**: при первом запуске `.env` создаётся из `.env.example` с новыми случайными паролями
   PostgreSQL, ClickHouse и MinIO, и установщик спрашивает в терминале: адреса трафика (по умолчанию
   все адреса машины), адрес панели, сеть установки для контейнеров (установщик предлагает
   свободную), нужны ли несколько узлов защиты за балансировщиком и сколько, запускать ли стандартный
   набор инспекторов (все, кроме `vlai`) и подходят ли стандартные память, копии и процессы. Порты
   80, 443 и 8081 спрашиваются только тогда, когда на машине их уже кто-то занял. Ответ «нет» на
   стандартный набор открывает вопросы за ним: по одному на инспектор, либо процессы nginx, копии
   каждого инспектора и память Redis. Enter берёт значение в скобках. Узел берёт имя машины, а если
   оно не подходит — `edge-01`. Установщик показывает план и применяет его после подтверждения.
   Лимиты CPU снижаются до числа ядер.
3. **Секреты**: ключ установки, реквизиты архива и четыре ключа подписи. Отпечаток ключа пишется в
   `secrets/contour-pin.json`; контейнер контроллера монтирует его только для чтения, и панель
   сверяет с ним ключ из API.
4. **Инфраструктура**: NATS, PostgreSQL, ClickHouse, оба Redis и MinIO; потоки JetStream и правила
   бакетов заводятся при старте.
5. **Схема**: на пустой базе контроллер сам ставит схему и данные поставки.
6. **Компоненты**: образы собираются по `sources.env` и запускаются.
7. **Раскладка**: запущенные инспекторы в каталоге, процессы nginx на узел, порты трафика и, если
   узлов несколько, haproxy перед ними. Где работает узел, на машине или в контейнере, следует из
   числа узлов и машины, см. [Где работает узел](#где-работает-узел).
8. **Панель**: сервер `panel` на узле за калиткой `auth` и пользователь `admin`. Пароль
   спрашивается сразу после настроек, до сборки (см. [Панель](#панель)).
9. **Рассылка**: все каналы конфигурации отправляются процессам, шаг ждёт их отчётов. Иначе свежая
   установка работала бы на умолчаниях образов, и панель показывала бы расхождение.
10. **Итог**: здоровье контейнеров одной строкой, адреса панели, API и трафика.

От каждого шага на экране остаётся строка с итогом и временем. Полный вывод сборки и compose
пишется в `install.log` рядом с `install.sh`; при ошибке установщик показывает его конец.

Без терминала или с `--defaults` ничего не спрашивается: настройка берётся из окружения, если она
там задана, иначе — значение по умолчанию.

```sh
PLC_NODE_ID=edge-02 PLC_PANEL_BIND=10.0.0.5 PLC_PANEL_PASSWORD=… ./install.sh install --defaults
```

### Смена настроек

```sh
./install.sh reconfigure
```

Те же вопросы, в скобках — текущие значения; порты тоже спрашиваются. «Да» на стандартный набор
возвращает стандарт: выключенный инспектор снова работает, копии и процессы становятся одной и
auto. Установщик показывает план и что меняется, а после подтверждения проходит установку заново: контейнеры с изменившимися настройками пересоздаются,
узлы и копии сверх новых чисел удаляются и сразу пропадают из панели, конфигурация рассылается
снова. Собираются только образы, которые нужны новым ответам и которых на машине нет, например
haproxy для второго узла. Данные остаются: внутренний Redis держит конфигурацию, которую забирают
узлы, на томе, и пересозданный узел применяет её без новой рассылки.

Новая сеть установки выводит все контейнеры из старой и запускает их в новой; данные остаются.
Контейнеры других проектов в этой сети, например приложение, куда маршруты ведут трафик, переезжают
вместе с ней под теми же именами.

Инспектор, которого ещё зовут маршруты или объявления, не выключается: установщик называет место и
останавливается, ничего не меняя. Без подтверждения, при отказе или прерывании `.env` остаётся
прежним. Пароли инфраструктуры не спрашиваются: они задаются при создании баз.

### Где работает узел

При одном узле (`PLC_NODES=1`) nginx с модулем работает прямо на машине, в контейнерах — только
остальное: агент узла берёт поколения у контроллера через NATS и перезагружает nginx, а тот слушает
порты трафика и порт панели сам. Для этого на машине нужны nginx той версии, под которую собран
модуль, сам модуль, агент и служба `placitum-node-agent`. В [образе машины](image/README.ru.md) они
есть; на другую машину установщик ставит их сам, если запущен от root на Debian или Ubuntu с
systemd (`image/host.sh node`: nginx с nginx.org, закреплённый на этой версии, модуль и агент из
образа узла). Иначе, а также если на машине свой nginx другой версии, узел — контейнер `edge`. Что
выбрано, видно в плане.

На машине nginx ходит к контейнерам по их постоянным адресам в сети установки: пулы панели смотрят
на контроллер и форму входа по адресу, а сводка печатает адреса контроллера, форм входа и капчи для
ваших пулов. Имена контейнеров там не разрешаются, а свой контейнер в сети установки после
перезапуска получает новый адрес, если его compose-файл не закрепит адрес (`ipv4_address` в верхней
половине сети) или не опубликует его порт на машине. Порты трафика — `http-<порт>` и
`https-<порт>` на адресе трафика; при нескольких адресах трафика nginx слушает все. Его логи — в
`/var/log/nginx`, поколения — в `/etc/nginx` и `/var/lib/waf`, агент виден в
`journalctl -u placitum-node-agent`.

При `PLC_NODES` больше одного все узлы — контейнеры: `edge`, `edge-02` и дальше. haproxy занимает
порты трафика и передаёт TCP-соединения всем узлам по PROXY protocol v2; узлы сами завершают TLS и
видят настоящий адрес клиента. haproxy и его агент работают прямо на машине, службами
`placitum-haproxy` и `placitum-haproxy-agent`, если они на машине есть или установщик может их туда
поставить тем же способом (`image/host.sh balancer`: haproxy из дистрибутива и агент из его образа);
иначе haproxy — контейнер `balancer`. Его агент в обоих случаях берёт конфигурацию у контроллера
через NATS. Переход от одного узла к нескольким и обратно данные не трогает: установщик останавливает
то, что машине больше не нужно, и запускает остальное.

Установщик при каждом запуске пишет `compose/layout.yml`: сеть установки, постоянные адреса, порты
трафика и, если узел на машине, адреса, которые контроллер печатает в конфигурацию узла. NATS, оба
Redis, MinIO, контроллер, формы, узлы и контейнер haproxy получают постоянные адреса в начале сети.
PROXY protocol включён на портах `http-8080` и `https-8443`, и узлы верят ему только от haproxy: с
адреса его контейнера или со шлюза сети, если haproxy работает на машине.

Порту трафика, созданному потом в панели, PROXY protocol тоже нужен. Панель остаётся на первом узле.
Конфигурация haproxy — на странице панели Конфигурация → haproxy; её точки входа задаёт установщик.

## Настройки

### `.env`

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | `placitum` | имя проекта compose; одно на оба файла, иначе установщик теряет свою же инфраструктуру |
| `PLC_TRAFFIC_BIND` | `0.0.0.0` | адреса трафика на хосте: все или адреса этой машины через запятую |
| `PLC_HTTP_PORT`, `PLC_HTTPS_PORT` | `80`, `443` | порты трафика на хосте |
| `PLC_PANEL_BIND` | `127.0.0.1` | IPv4-адрес машины, на котором узел отдаёт панель: `127.0.0.1` — только с этой машины, адрес внутреннего интерфейса — из его сети, `0.0.0.0` — со всех адресов |
| `PLC_PANEL_PORT` | `8081` | порт панели на этом адресе |
| `PLC_CONTROLLER_PORT` | `8080` | API контроллера без входа, только на `127.0.0.1` |
| `PLC_SUBNET` | свободная сеть | сеть установки для контейнеров, от /16 до /24; NATS, оба Redis, MinIO, контроллер, формы, узлы и контейнер haproxy получают постоянные адреса в её начале, остальные контейнеры — в верхней половине |
| `PLC_NODE_ID` | имя машины, иначе `edge-01` | имя узла в панели, пульсе и аудите; не спрашивается |
| `PLC_PANEL_LOGIN` | `admin` | логин администратора панели; не спрашивается, образ машины ставит логин машины |
| `PLC_COOKIE_SECURE` | `off` | `on` — куки калитки и капчи только по TLS; пока узел работает по HTTP, оставьте `off` |
| `POSTGRES_*`, `CLICKHOUSE_*`, `MINIO_ROOT_*` | пользователь `waf`, случайные пароли | реквизиты инфраструктуры, пишутся при создании `.env`; для внешних баз поменяйте и адреса в `compose/waf.yml` |
| `PLC_REDIS_EXCHANGE_MB`, `PLC_REDIS_INTERNAL_MB` | `2560`, `512`; при 8 ГБ и меньше `640`, `320` | память Redis обменника (объекты запросов, ждущих вердикта) и внутреннего Redis (конфигурация, состояние инспекторов), МБ; под данные Redis берёт 80% |
| `PLC_NODES` | `1` | узлов защиты на машине: один — nginx прямо на машине, где это возможно, больше одного — контейнеры за haproxy, см. [Где работает узел](#где-работает-узел); спрашивается как «несколько узлов за балансировщиком?», потом сколько |
| `PLC_NGINX_WORKERS` | `auto` | процессов nginx на узел; установщик выставляет это в панели |
| `PLC_COPIES_<ИНСПЕКТОР>` | `1`, у `VLAI` `0` | копий каждого инспектора; 0 выключает его, `AUTH` нужен хотя бы один для входа в панель |
| `PLC_CPUS`, `PLC_CPUS_NATS`, `PLC_CPUS_KEEPER` | `2`, `6`, `4` | лимит CPU сервиса, NATS и keeper; установщик снижает их до числа ядер |
| `PLC_CPUS_EDGE` | по процессам nginx | лимит CPU узла |
| `NGINX_VERSION` | `1.28.0` | версия nginx для модуля и базового образа; меняются только вместе |

### `sources.env`

Откуда берётся каждый компонент: git-адрес с веткой или тегом либо путь на диске. Этот файл и есть
версия установки. `#rc_1.0.1` — кандидат в выпуск, рабочие установки ставятся по тегам. Встроенных
умолчаний у контекстов сборки нет: компонент без строки в `sources.env` не соберётся.

### Секреты

`secrets/` в git не лежит. Ключ установки (RSA-4096) видят агент узла и `crypto`, контроллер
получает только публичную половину. Ключи подписи: `auth.hmac` и `auth-app.hmac` у калитки,
`captcha.hmac` у капчи, `cookie.hmac` у инспектора кук; друг с другом они не делятся. Реквизиты
архива лежат файлом в формате профиля AWS. Пароля `admin` в `secrets/` нет: в список
пользователей уходит только его bcrypt.

Перевыпуск ключа установки (`bootstrap/secrets.sh --force`) сбрасывает доверие: сертификаты,
загруженные через панель, перестанут расшифровываться. Перевыпуск ключа подписи разлогинивает
всех, кого он подписывал, и больше ничего не делает.

## Что запускается

Восемь сервисов инфраструктуры и сам Placitum: узел защиты, контроллер с панелью, логгер и поиск,
`crypto`, `geo`, `keeper`, девять инспекторов (`ip`, `modsec`, `json`, `counter`, `action`,
`rewrite`, `cookie`, `auth` с формой входа, `captcha` с виджетом) и три агента наблюдения.
Каждый инспектор работает в `PLC_COPIES_<ИНСПЕКТОР>` копиях; инспектор без копий не запускается, и
его не видят ни панель, ни маршруты. Классификатор текста `vlai` по умолчанию выключен: с
`PLC_COPIES_VLAI=1` его собирает и запускает `./install.sh reconfigure`.

Наружу открыты только трафик и панель: порты трафика на `PLC_TRAFFIC_BIND` и панель на
`PLC_PANEL_BIND`, `PLC_PANEL_PORT`. Если узлов несколько, порты трафика занимает haproxy. Контроллер
опубликован только на `127.0.0.1`. Формы входа, виджет капчи, поиск и `crypto` остаются внутри сети:
к ним ходят только узел и контроллер.

## После установки

1. Откройте панель на `http://127.0.0.1:8081` (или на адресе из `PLC_PANEL_BIND`) и войдите как
   `admin` с паролем из установки. В панели одно пространство `default`, каталог инспекторов,
   профили поставки и один сервер — сама панель (`panel`). Других серверов и маршрутов нет, их
   заводит оператор.
2. Заведите первый маршрут: сервер с привязкой к порту `http-8080` (он есть в поставке: узел
   слушает 8080 внутри контейнера, снаружи это `PLC_HTTP_PORT`), путь, апстрим и инспекторы на
   маршруте. Инспектор, которого зовёт маршрут, должен быть объявлен на пространстве (страница
   пространства, инспекторы), иначе сборка ответит `undeclared_inspector`. WAF на сервере или пути
   включается явно настройкой `waf` маршрута: по умолчанию он выключен, и без неё модуль молча
   пропускает маршрут с инспекторами. Разошлите конфигурацию: узел применит её через
   `nginx -s reload` и отчитается.
3. Отправьте запрос через узел: `curl -i http://<хост>/…` вернёт ответ апстрима, а через несколько
   секунд в журнале панели появится запись с вердиктом.
4. Каталог гео (страны и ASN) заливается отдельно: у выгрузки MaxMind своя лицензия, и в образы она
   не входит. Без неё правила по стране отказывают с кодом ошибки, остальное работает.

## Проверка

```sh
./install.sh status                                                          # сервисы
docker compose --env-file .env --env-file sources.env -f compose/waf.yml ps
curl -fsS http://127.0.0.1:8080/healthz                                      # контроллер
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/api/spaces   # панель без входа: 401
docker compose exec -T nats-box nats stream ls                               # потоки WAF_AUDIT и WAF_LOG
```

Здоровая установка: все сервисы с healthcheck в состоянии `healthy`, остальные каждые четыре
секунды пишут в журнал кадр присутствия. Страница состояния в панели показывает то же самое
понятнее.

## Панель

Панель отдаёт узел защиты, а не контроллер: сервер `panel` на порту 8081 контейнера, за калиткой
`auth`. Шаг установщика panel (`bootstrap/panel.mjs`) заводит это через API изнутри контейнера
контроллера. Повторный `./install.sh panel` заводит только недостающее и правки оператора не
трогает; `admin` создаётся, только если список пользователей пуст. Тот же запуск чинит панель, у
которой удалили сервер, путь или пул.

Пароль `admin` спрашивается сразу после настроек, до сборки, дважды и без эха. Нигде не хранится: в
список пользователей уходит только bcrypt. Enter при первой установке — пароль сгенерирует шаг
panel и покажет один раз; при повторных запусках пароль остаётся прежним. Без терминала пароль
берётся из `PLC_PANEL_PASSWORD` в окружении. Сменить пароль и заодно снять блокировку входа:

```sh
./install.sh panel-password
```

Каждый запрос через калитку панели помечен в аудите меткой `panel` рядом с пользователем сессии:
кто что делал в панели, ищется фильтром `marker=panel`. Аудит хранит срезы заголовков и аргументов
запросов панели, архив — запросы целиком на сутки; кука сессии, `Authorization` и аргумент
`password` сохраняются хешем. Тела не хранятся у выгрузки гео и у заведения пользователя.

Где слушает панель, решает `PLC_PANEL_BIND`. Docker публикует порт на адрес, а не на интерфейс, и
адрес обязан быть на машине: иначе не поднимется узел, а с ним и трафик. `./install.sh check` это
проверяет. Фаервол машины здесь не граница: Docker проводит опубликованные порты мимо UFW. Всё,
что шире loopback, отдавайте по TLS, иначе пароль идёт открытым текстом.

Контроллер без входа слушает только `127.0.0.1:8080` (`PLC_CONTROLLER_PORT`): его API нужен
`install.sh` и для аварийного входа, когда лежит узел или калитка. С другой машины — через туннель:

```sh
ssh -L 8080:127.0.0.1:8080 <хост>
```

Этот порт нельзя проксировать ничем: nginx на хосте или любой обратный прокси перед
`127.0.0.1:8080` снова откроет API без входа. Если прокси нужен, ставьте его перед портом панели
(`PLC_PANEL_PORT`) и передавайте через него `Host` браузера (в nginx —
`proxy_set_header Host $host;`): контроллер отклоняет изменение, у которого `Origin` называет
другой хост, чем `Host`, и отвечает `403 cross_origin`.

Сессия панели живёт 8 часов, продлевается незаметно и заканчивается окончательно через 24 часа
после входа (`session.max_ttl_s` источника `panel`). Пользователю, которого удалили из
`panel_users` или которому сменили пароль, сессия больше не продлевается: она закончится вместе с
текущим токеном, самое позднее через 8 часов (`session.ttl_s`).

Без аварийного входа под рукой не трогайте: калитку на путях `/` и `/agent_health_socket` сервера
`panel`, источник и профиль `panel`, последнего пользователя в `panel_users`. Калитка, снятая с
`/`, открывает панель без пароля.

## Порты инфраструктуры

По умолчанию PostgreSQL, Redis, NATS, ClickHouse и MinIO снаружи не видны: они живут в сети
compose, наружу открыты только узел и панель. Чтобы ходить к ним с самой машины (`psql`,
`clickhouse-client`, консоль MinIO), поставьте в `.env` `PLC_INFRA_PORTS=loopback` и снова
запустите `./install.sh install`: порты появятся на 127.0.0.1. На 0.0.0.0 они не публикуются
никогда.

## Версия сборки

`install.sh` берёт версию из тега core (без тега — `dev`) и ревизию из его коммита и передаёт их в
каждую сборку. Их видно в метках образов, в строке `build` при старте каждого процесса
(`docker compose logs keeper | grep build`) и в кадре присутствия на странице состояния. Задать
вручную: `PLC_VERSION` и `PLC_REVISION` в `.env`.

## Обновление

Соберите новые образы и перезапустите по порядку: инфраструктура, инспекторы, контроллер, узел.
Схема PostgreSQL на живой базе не обновляется: если в новой версии она изменилась, установку ставят
заново, на пустой том. Команды для обновления одним вызовом пока нет.

## Грабли

- **Порты 80 и 443 заняты** другим сервисом: установка упадёт на узле. Укажите другие порты, когда
  установщик спросит, или позже через `./install.sh reconfigure`.
- **Сеть установки пересеклась с сетью, которая появилась у машины позже**, например с маршрутом
  VPN: контейнеры теряют эту сеть. Выберите другую сеть установки через `./install.sh reconfigure`.
- **Имя узла в двух местах**: `PLC_NODE_ID` в `.env` и `waf_node_id` в `config/edge/node.conf`.
  `install.sh` держит их вместе; правите руками — правьте оба.
- **Не меняйте `COMPOSE_PROJECT_NAME` на работающей установке**: новое имя — новый проект, а старые
  контейнеры и тома остаются под старым.
- **Windows (Docker Desktop)**: сборщик bake не понимает git-адреса источников на Windows
  (`failed to evaluate path "https://…git#rc_1.0.1"`). Установка рассчитана на Linux; на Windows
  перед `install` поставьте `COMPOSE_BAKE=false` в окружении.
- **Секрет поправили руками, и сервис упал с `permission denied`**: процессы в образах работают от
  своих пользователей и читают файл секрета через монтирование как есть. Файлы в `secrets/` имеют
  права `0644`, каталог — `0700`; `sh bootstrap/secrets.sh` выставит права заново, ничего не
  перевыпуская.
